1. Executive Summary

Nexus is an ambitious full-stack career intelligence platform that aims to scrape public job boards, normalize listings via LLM extraction, match them to uploaded resumes using vector similarity, and deliver results through an AI agent and video briefings. The codebase demonstrates strong architectural vision but contains significant implementation gaps, security vulnerabilities, and non-functional scraping that must be addressed before any production deployment.

⚠️ KEY FINDING: The scrapers do NOT reliably pull data from real websites.

The YC Jobs scraper targets workatastartup.com which is a JavaScript-rendered SPA — httpx + BeautifulSoup will receive an empty shell. The GitHub Internships scraper targets an outdated repository URL that may have moved or changed format. Neither scraper has been validated against live production pages.

3. Scraping System Audit — Does It Actually Work?

VERDICT: The scraping system does NOT reliably pull data from real websites.

3.1 YC Jobs Scraper (yc_jobs.py)

Targethttps://www.workatastartup.com/jobs
Methodhttpx GET → BeautifulSoup HTML parsing
Works?NO

Issues Found:

  1. JavaScript-Rendered SPA (Critical): workatastartup.com is a React single-page application. When httpx fetches the page, it receives a minimal HTML shell with a <div id="root"></div> and JavaScript bundles. BeautifulSoup cannot parse job cards that are rendered client-side. The CSS selectors (.job-card, .company-job-listing) will match zero elements.
  2. Hardcoded Fallback Values (Medium): Line 54 falls back to "Software Engineer" when no title is found. Line 58 falls back to "YC Startup" when no company is found. This means if the parser partially works, it produces fabricated data that looks real.
  3. Overly Generic CSS Selectors (Medium): Selectors like h2, h3, h4, .job-title, [class*='title'] are dangerously broad. They will match navigation elements, sidebar headings, and footer text if any HTML is returned.
  4. No Pagination Handling (Low): The discover_pages method returns hardcoded URL variants rather than dynamically discovering pagination links.

3.2 GitHub Internships Scraper (github_jobs.py)

Targethttps://raw.githubusercontent.com/pittcsc/Summer2025-Internships/dev/README.md
Methodhttpx GET → Regex-based markdown table parsing
Works?PARTIALLY — with significant caveats

Issues Found:

  1. Outdated Repository URL (Critical): The URL targets pittcsc/Summer2025-Internships on the dev branch. This repository has been restructured and renamed to SimplifyJobs/Summer2025-Internships with a main branch. The current URL will return a 404.
  2. Brittle Regex Parsing (High): The markdown table parsing relies on exact formatting. The Simplify repo uses emoji (✅, 🔒), nested markdown links, multi-line cells, and collapsed sections (<details>/<summary>) that will break the regex-based parser.
  3. No Content-Type Validation (Medium): scrape_page checks if <table appears in the raw text to decide between HTML vs markdown parsing. Raw markdown from GitHub will contain literal | pipe characters, and the regex parser will engage, but edge cases (markdown with embedded HTML tables) may confuse the dispatcher.

4. Security Vulnerability Assessment

4.1 Critical Vulnerabilities

SEC-001: JWT Stored in localStorage (XSS Attack Vector)

File: apps/web/lib/auth-context.tsx (Lines 67, 77) and apps/web/lib/api.ts (Line 24)

Risk: Any XSS vulnerability anywhere in the application allows an attacker to steal the JWT token and impersonate any user. localStorage is accessible to all JavaScript on the page.

Fix: Migrate to HttpOnly, Secure, SameSite=Lax cookies. The backend should set the cookie, and the frontend should never touch the token directly.

SEC-002: No Rate Limiting on Authentication Endpoints

File: apps/api/app/services/auth_service.py

Risk: The /auth/login and /auth/register endpoints have no rate limiting. An attacker can perform unlimited brute-force credential stuffing attacks. No account lockout after failed attempts.

Fix: Add slowapi or a custom rate limiter middleware. Implement account lockout after 5 failed attempts with exponential backoff.

SEC-003: Hardcoded Secret Key in Source Code

File: apps/api/app/core/config.py (Line 35)

Risk: Default SECRET_KEY = "nexus_super_secret_dev_key_change_in_production_32chars!" is committed to version control. If deployed without changing, all JWTs are signed with a known key.

Fix: Remove the default value entirely. Make the key required and fail to start without it. Add startup validation.

SEC-004: Docker Container Runs as Root

File: apps/api/Dockerfile

Risk: No USER directive in the Dockerfile. The application runs as root inside the container. Any container escape vulnerability gives root access to the host.

Fix: Add RUN useradd --create-home appuser and USER appuser before CMD.

4.2 High Severity Vulnerabilities

SEC-005: Hardcoded Database Credentials

Files: docker-compose.yml (Lines 9-10, 48-49, 70-71), alembic.ini (Line 36), .env.example

Risk: Database passwords (postgrespassword) are duplicated across multiple files and committed to version control.

SEC-006: 24-Hour JWT Expiry Without Refresh Token Rotation

File: apps/api/app/core/config.py (Line 37): ACCESS_TOKEN_EXPIRE_MINUTES = 60 * 24

Risk: A stolen token is valid for 24 hours. No refresh token mechanism exists, so there's no way to revoke a compromised session short of rotating the entire SECRET_KEY.

SEC-007: CORS Allows All Methods and Headers

File: apps/api/app/main.py (Lines 36-37): allow_methods=["*"], allow_headers=["*"]

Risk: Overly permissive CORS configuration. Should restrict to only the HTTP methods and headers actually used (GET, POST, PUT, DELETE + Authorization, Content-Type).

SEC-008: Aggressive Logout on Network Error

File: apps/web/lib/auth-context.tsx (Lines 49-52)

Risk: The refreshUser function clears localStorage and logs the user out if /auth/me throws any error — including transient 503 errors or network failures. This creates a poor user experience and can be weaponized as a denial-of-service attack by inducing temporary network failures.

4.3 Medium Severity Issues

SEC-009: No Input Validation on Scraper-Sourced Data

Raw HTML content from scrapers is stored directly in the database without sanitization. If this data is ever rendered in the frontend without escaping, it creates a stored XSS vector.

SEC-010: No CSRF Protection

While JWT bearer tokens provide some CSRF resistance, the frontend uses credentials: true in CORS. If migrated to cookie-based auth, CSRF tokens must be added.

SEC-011: Password Policy Not Enforced

The registration endpoint accepts any password string. No minimum length, complexity, or common password checks are enforced.

5. Backend API Audit (FastAPI / Python)

5.1 Code Quality Issues

BK-001: ScraperService is a God Class

File: apps/api/app/services/scraper_service.py

This service orchestrates scrapers, manages database persistence (RawListingRepository.upsert_candidate), and computes statistics. It violates the Single Responsibility Principle. Persistence logic should be separated from scraper orchestration.

BK-002: Missing Database Transaction Rollbacks

Files: scraper_service.py, auth_service.py

Database operations are not wrapped in explicit try/except with await db.rollback(). If an exception occurs mid-transaction, the SQLAlchemy session can become corrupted for subsequent requests using the same connection pool.

BK-003: Broad Exception Catching

File: scraper_service.py (Line 58)

except Exception as exc catches everything, hiding specific errors like IntegrityError (database constraint violations) vs TimeoutError (network issues). These should be handled differently.

BK-004: Global Lock Bottleneck in Rate Limiter

File: apps/api/app/scraping/rate_limiter.py (Line 18)

The _global_lock creates a bottleneck when multiple scrapers target different hosts. Acquiring a host-specific lock requires first acquiring the global lock, serializing all host lock creation operations.

BK-005: No Graceful Shutdown for Async HTTP Client

File: apps/api/app/scraping/client.py (Line 55)

PoliteScraperClient creates a new httpx.AsyncClient per request inside an async with block. This prevents connection pooling. A single long-lived client should be initialized during app startup and shared across scraper runs.

BK-006: pages_scraped Reports max_pages, Not Actual Pages

File: scraper_service.py (Line 67)

ScrapeSummary.pages_scraped is set to max_pages rather than the actual number of pages that were successfully scraped. This produces inaccurate metrics.

5.2 Architecture Observations

  • Positive: Clean layered architecture (routes → services → repositories → models) with proper dependency injection via api/deps.py.
  • Positive: Pydantic v2 schemas for request/response validation with proper model_validate usage.
  • Positive: Versioned API routes under /api/v1/ with a centralized router.
  • Positive: Request context middleware with request IDs and response timing.
  • Negative: Workers module (workers/__init__.py) is empty — Celery integration is scaffolded but not implemented.
  • Negative: Global exception handler (Line 84-97 of main.py) properly sanitizes output, but should differentiate behavior between DEBUG=true and production modes.

6. Frontend Audit (Next.js / React)

6.1 Critical Issues

FE-001: Complete Abandonment of Server Components

Every page file uses "use client", including the landing page (app/page.tsx). This eliminates all benefits of Next.js 14/15's Server Components: no SSR/SSG, no server-side data fetching, no streaming, degraded SEO, and larger JavaScript bundles. The entire app is effectively a client-side SPA with Next.js routing.

FE-002: Broken Mobile Navigation

File: apps/web/components/Navbar.tsx (Line 65)

Navigation links are hidden on smaller screens (hidden md:flex) but no mobile hamburger menu fallback exists. Mobile users literally cannot navigate the application after landing.

6.2 High Severity Issues

FE-003: Monolithic Page Components

app/discover/page.tsx (370+ lines) and app/resume/page.tsx (380+ lines) mix data fetching, local state, derived state, and massive UI markup. These need decomposition into composable sub-components (ListingCard, UploadDropzone, FilterBar).

FE-004: Silent API Error Handling

File: app/discover/page.tsx (Line 95)

The handleSearch function has an empty catch block. If the search API fails, no error feedback is shown to the user and the UI remains stuck in a loading state.

FE-005: Double Image Loading

Files: login/page.tsx, signup/page.tsx, Navbar.tsx

Both light and dark mode logos are loaded in the DOM via next/image and toggled via CSS. The browser downloads both images regardless of active theme, wasting bandwidth.

FE-006: apiClient Cannot Handle FormData

File: apps/web/lib/api.ts (Line 27)

The API client hardcodes Content-Type: application/json. This breaks file uploads (FormData), forcing resume/page.tsx to implement a custom raw fetch call, duplicating auth token extraction and error handling.

6.3 Medium Severity Issues

FE-007: Inefficient Polling for Resume Processing

app/resume/page.tsx uses React Query's refetchInterval: 2000 to HTTP-poll the server every 2 seconds to check resume processing status. This is expensive; consider SSE or WebSockets.

FE-008: Widespread any Type Usage

catch (err: any) is used in login, signup, resume, and agent pages. Should use catch (err: unknown) with instanceof checks.

FE-009: Inline/Duplicated Type Definitions

Interfaces like ListingItem, ChatMessage, and BriefingRecord are declared inline within individual page files. These should be centralized in a types/ directory to prevent drift and duplication.

FE-010: SSR Authentication Failure

The apiClient reads tokens from window.localStorage. If any Server Component attempts authenticated API calls, it will crash since window is undefined during SSR.

7. DevOps & Infrastructure Audit

7.1 Dockerfile Issues

DO-001: No Multi-Stage Build

build-essential, curl, and libpq-dev are installed and remain in the final image. Attack surface is unnecessarily large. Image size is bloated. Should use a builder stage to compile dependencies, then copy only the runtime artifacts to a slim final stage.

DO-002: No Health Check in Dockerfile

While docker-compose.yml has healthchecks for Postgres and Redis, neither the API nor worker Dockerfiles include a HEALTHCHECK instruction.

7.2 Docker Compose Issues

DO-003: Environment Variable Duplication

Database URLs are duplicated verbatim between the api and worker services. Should use YAML anchors (x-env) or env_file for DRY configuration.

DO-004: Redis Port Mismatch

.env.example sets REDIS_URL=redis://localhost:6339/0 (port 6339) but docker-compose.yml exposes Redis on standard port 6379. This will cause connection failures.

DO-005: Missing Production APP_ENV

docker-compose.yml hardcodes APP_ENV=production in what is clearly a local development compose file. This could mask debugging issues during development.

7.3 CI/CD — Completely Missing

DO-006: No CI/CD Pipeline

There are no .github/workflows, no GitLab CI configs, no automated linting (ruff, eslint), no testing automation, no security scanning (bandit, trivy), and no container image building pipelines.

7.4 Monitoring — Absent

DO-007: No Monitoring or Alerting

SENTRY_DSN exists in .env.example but sentry-sdk is not in the dependencies. No Prometheus metrics endpoint. No Celery monitoring (Flower). Docker container logging is not capped, which will cause disk exhaustion.

8. Database Design & Performance Audit

DB-001: UUIDv4 Primary Keys Cause Index Fragmentation

All models use random UUIDv4 strings (String(36)). UUIDv4's random distribution causes B-tree index fragmentation, which degrades INSERT performance as tables grow to millions of rows. Recommendation: Use UUIDv7 (time-ordered) or ULID.

DB-002: Missing pgvector Index for Embedding Search

The Listing model stores embeddings using CompatibleVector(384), but no HNSW or IVFFlat index is created for this column. Without a specialized vector index, all nearest-neighbor queries will perform a full table scan.

DB-003: Alembic Hardcoded Database URL

File: apps/api/alembic.ini (Line 36)

sqlalchemy.url is hardcoded to postgresql://postgres:postgres@localhost:5432/nexus. Should be read from SYNC_DATABASE_URL environment variable dynamically in migrations/env.py.

DB-004: No Connection Pool Configuration

The app uses both async (asyncpg) and sync (psycopg2) connections. Neither pool has explicit size limits (pool_size, max_overflow). Under load, this can exhaust PostgreSQL's max_connections.
